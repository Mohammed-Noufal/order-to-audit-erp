1. How this design earns the marks
The brief says business modelling beats feature count, and 65% of the weight sits in four
things: benchmark numbers (30), production/inventory design (20), sales-to-invoice flow
(15), data model and code quality (15). The design below is shaped around those.

Production and inventory (20%) Insert-only stock ledger, BOM with planned vs

Sales-to-invoice (15%) Order, approve (stock check), invoice (GST),

2. Five design rules
1. Balance = SUM of ledger. No balance column anywhere that a person or a bug can

overwrite.
2. Exact arithmetic. BigDecimal in Java, DECIMAL in MySQL: money 2 dp, rates 4 dp,

quantities 3 dp. Rounding is HALF_UP, done once per line, and written in the README.
Why not integer paise? Rates like Rs 45 per kg become fractions of a paisa per gram,
so DECIMAL with an explicit scale is clearer and safer.

3. One stock unit per item (kg, L or pcs). Anything entered in g or ml is converted on the
way in by a Unit enum, so the ledger only ever holds the stock unit. Cartons are not a
unit: a carton is a packaging item, and finished packets per carton is a column on the
item.

4. Posted documents are frozen. An invoice is cancelled with a credit note, never
deleted. Edits write audit_log with user, time, old and new JSON.

5. One door to the ledger. Only StockService.post() writes ledger rows. Every other
service calls it.

3. Stack (and the 3-sentence justification for your README)
Java 21, Spring Boot 3, Spring Data JPA, MySQL 8, Spring Security with JWT, Flyway,
OpenPDF (PDF), OpenCSV and Apache POI (CSV/Excel), JUnit 5 with Testcontainers
(or H2 in MySQL mode), Docker Compose.
Frontend: a responsive PWA or simple React app that only consumes this API. The
salesman screens are mobile-first.
README wording: We chose a Spring Boot monolith on MySQL because the problem
is transactional: a dispatch or production run must change several tables atomically,
and a relational database with transactions gives that for free. A single deployable
keeps setup to one docker compose command. JWT roles map directly to the five
users in the brief.

Why it is shaped this way
One ITEMS table for raw, packaging and finished goods (item_type column). The
ledger then needs just one item_id, and stock summary is one query with a filter.
BOMS is separate from ITEMS and items.bom_id points to it. That is what lets two
pack sizes share one recipe later (see section 12).
STOCK_LEDGER.source_type + source_id is the traceability link (PURCHASE,
PRODUCTION_RUN, INVOICE, CREDIT_NOTE, ADJUSTMENT). It is a polymorphic
reference, so it is not a database FK. Index on (item_id, movement_date) and
(source_type, source_id).
Snapshots on invoice lines (rate, HSN, GST rate, customer GSTIN): editing a master
later never changes a posted invoice.
Movement types and sign: OPENING +, PURCHASE +, PROD_ISSUE -,
PROD_OUTPUT +, SALE_DISPATCH -, SALE_RETURN +, ADJUSTMENT +/-.
Status flows: Order SUBMITTED -> APPROVED -> INVOICED -> DISPATCHED (or
SUBMITTED -> REJECTED). Invoice POSTED -> CANCELLED. Run DRAFT -> ISSUED -
> COMPLETED.

6. API conventions
Base path /api , JSON, Authorization: Bearer <jwt> . Dates ISO (2026-11-25).
Quantities in requests carry a unit, e.g. {itemId: 3, qty: 10500, unit: ML} . The
server converts to the item stock unit.
Error body: {timestamp, status, error, message, details[]} . Codes: 400
validation, 401 not logged in, 403 wrong role, 404 not found, 409 business-rule conflict
(insufficient stock, wrong status, overpayment).
Lists accept page , size . Reports accept from , to , format .
Examples below use loose JSON without quotes to save space; real requests use
normal JSON.

8.1 Unit conversion

enum Unit { // dimension, factor to the dimension base (kg, L, pcs)
  KG(MASS,1), G(MASS,0.001), L(VOLUME,1), ML(VOLUME,0.001), PCS(COUNT,1), 
PACKET(COUNT,1);
}
BigDecimal toStockUnit(BigDecimal qty, Unit entered, Item item) {
  if (entered.dimension != item.stockUnit.dimension) throw new 
BadRequest(unit mismatch);
  return qty.multiply(entered.factor).divide(item.stockUnit.factor, 3, 
HALF_UP);
}
// 10500 ML on an item stored in L -> 10.500

8.2 StockService.post (the only door to the ledger)

@Transactional(propagation = MANDATORY)      // must run inside the caller's 
transaction
LedgerEntry post(Item item, MovementType type, BigDecimal delta, BigDecimal 
unitCost,
                 SourceType src, Long srcId, LocalDate date) {
  itemRepo.lockById(item.getId());           // SELECT ... FOR UPDATE: two 
dispatches cannot both pass the check
  BigDecimal bal = ledgerRepo.sumDelta(item.getId());
  if (delta.signum() < 0 && bal.add(delta).signum() < 0)
      throw new InsufficientStockException(item, bal, delta.negate());   // -
> HTTP 409
  return ledgerRepo.save(new LedgerEntry(item, date, type, delta, unitCost, 
src, srcId, currentUser()));
}

Because every business action calls this inside one @Transactional method, a failure
halfway (for example the third material is short) rolls back the first two ledger rows. That
is the answer to 'what if it crashes midway' in the interview.

8.3 Purchase (weighted average cost)

for (line : request.lines) {
  qty = toStockUnit(line.qty, line.unit, item);
  before = stock.balance(item);
  newAvg = before.multiply(item.avgCost).add(qty.multiply(line.rate))
             .divide(before.add(qty), 4, HALF_UP);
  stock.post(item, PURCHASE, qty, line.rate, PURCHASE, purchase.id, date);
  item.setAvgCost(newAvg);   // flour: (100*42 + 60*45)/160 = 43.1250
}

Costing method to state: perpetual weighted average. Chosen over FIFO because a small
factory mixes batches of flour in one bin, so layer tracking would pretend a precision that
does not exist. Last price is too jumpy for a margin report. Every issue ledger row stores
the unit_cost used, so any cost is re-derivable.

8.4 Production run (the heart of the marking)
Create (status DRAFT): for each BOM line, planned_qty = qty_per_batch x batches;
expected_output = yield_packets x batches. Insert RUN_LINES with actual_qty = 0. No
stock moves yet.
Issue (DRAFT or ISSUED): for each requested item, convert unit, stock.post(item,
PROD_ISSUE, -qty, item.avgCost, PRODUCTION_RUN, run.id) , add to the run line
actual_qty. A material not in the BOM is allowed but creates a new run line with planned 0
(extra issue), which shows as flagged.

runUnitCost  for finished goods = material cost / actualOutput at completion. It is only for
stock valuation; the final cost per packet (with overheads) is calculated in 8.5.

8.5 Costing (computed on read, never stored)

materialCost = SUM(-qty_delta * unit_cost) of ledger rows where source = this 
run and type = PROD_ISSUE
overhead     = SUM(run_overheads.amount)
costPerPacket = (materialCost + overhead) / actualOutput      -> 4 dp 
internally, shown 2 dp HALF_UP
margin        = sellingPrice - costPerPacket;  margin% = margin / 
sellingPrice

Rules to write down: (a) all cost of the run, including the 6 damaged pouches, is absorbed
by good packets, which is the normal-loss convention. (b) Labour and gas/power are
entered per run. If you later add monthly shared overheads (rent, supervisor pay), allocate
them to runs pro rata to packets produced that month, and say so. Computing on read
means a late overhead entry (step 8 arrives after the run) can never leave a stale stored
number.

8.7 Stock check and approval

// aggregate lines per item first, then:
available = stock.balance(fgItem);
shortage  = max(0, requested - available);

GET /stock-check returns the table. POST /approve: if any shortage and allowBackorder is
false -> 409 with the shortage list. Admin then has three honest options: reduce the
quantity with PUT (to 88), reject, or approve with allowBackorder = true. Rule to
document: the check at approval is advisory so the admin can decide; the check at
dispatch is hard, because StockService refuses negative stock.

8.11 Cancel with credit note
Only POSTED invoices. Reason mandatory. Reject with 409 if payments exist (assumption:
refund handled outside). Create CREDIT_NOTES mirroring the invoice amounts (number
series CN/2026-27/0001). If it was dispatched, post SALE_RETURN +qty for each line.
Invoice -> CANCELLED, order -> CANCELLED. Write audit_log. GST report subtracts
credit notes in the month they are issued.

8.12 Audit trail
One AuditService.log(entityType, id, action, before, after)  called from the
services that change documents: order edit, approve/reject, invoice create/cancel, run
complete, adjustment, master edits. Before and after are JSON snapshots. Do not build
AOP magic; explicit calls are easier to explain.

8.13 Reports
Each report is one query returning rows, plus a shared Exporter  that turns rows into
json, csv, xlsx or pdf. The stock ledger report is the one that proves 'opening + receipts -
issues = closing':

SELECT item_id,
  SUM(CASE WHEN movement_date <  :from THEN qty_delta ELSE 0 END)               
AS opening,
  SUM(CASE WHEN movement_date BETWEEN :from AND :to AND qty_delta > 0 THEN 
qty_delta ELSE 0 END) AS receipts,
  SUM(CASE WHEN movement_date BETWEEN :from AND :to AND qty_delta < 0 THEN -
qty_delta ELSE 0 END) AS issues,
  SUM(CASE WHEN movement_date <= :to THEN qty_delta ELSE 0 END)                 
AS closing
FROM stock_ledger GROUP BY item_id;

GST summary groups invoice lines by supply_type and gst_rate (taxable, CGST, SGST,
IGST), splits B2B (customer has GSTIN) from B2C, then subtracts credit notes. That shape
maps to GSTR-1 tables and the GSTR-3B outward supply figures.

12. Interview-proofing
Add a 500 g pack sharing the same BOM. Insert a new finished item with
pack_size_g = 500  and the same bom_id . Expected output = bom.yield_packets x

batches x bom.ref_pack_g / item.pack_size_g, so a 40 kg batch gives 80 packets of
500 g. Packaging lines on the BOM are per packet for the reference pack, so scale
them by the same ratio. Know this sentence cold.
Why no stored balance? Two screens updating one number can drift. A sum of
immutable rows cannot.
Why is costing computed on read? Overheads arrive after the run; nothing stored
can go stale.
What if two admins dispatch the last 88 packets at once? The item row lock in
StockService.post serialises them; the second gets 409.

13. README and design note checklist
README: setup (one docker compose up), test logins per role, stack justification (section
3), features against Must / Should / Stretch, benchmark table with your numbers and the
two explanations in section 9, assumptions, known gaps.
Assumptions to write down: financial year April-March; factory state code 33 (Tamil
Nadu); GST 5% flat from the item master; no invoice round-off; tolerance 3% and flagged
only when strictly beyond; packaging consumption recorded at run completion; shortage
is advisory at approval and hard at dispatch; one payment settles one invoice; no advance
payments; whole-invoice dispatch only; weighted average costing; overheads entered per
run; damaged pouches absorbed in good-packet cost.
Known gaps (honest ones score better than hidden ones): partial dispatch and sales
returns other than cancellation, batch and expiry tracking, offline sync is idempotent-
server-side only, no e-invoice or Tally export.
Design note (2 pages max): the ER diagram from section 4, one paragraph on how stock
is the sum of the ledger, one paragraph on BOM consumption and variance (8.4), one
paragraph on costing (8.5). Reuse the text above in your own words.
